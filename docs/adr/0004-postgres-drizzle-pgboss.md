# ADR-0004 — PostgreSQL, Drizzle, and pg-boss as job queue and outbox

## Context and problem statement

The app needs relational storage, durable background jobs (AI tasks over many sessions, with progress, stop and retry) and reliable domain events. The prototype kept job state in memory and lost it on restart. Self-hosters should run as few services as possible.

## Decision drivers

- Minimum number of runtime services (self-hosting).
- Events must not be lost or sent for a rolled-back transaction.
- Typed SQL, versioned migrations.

## Considered options

- **Database**: PostgreSQL · SQLite · MongoDB
- **Data access**: Drizzle · Prisma · Kysely
- **Jobs/events**: pg-boss · BullMQ (Redis) · outbox table + custom relay · cloud queues

## Decision outcome

- **PostgreSQL** (available everywhere, managed or in Docker).
- **Drizzle ORM** (0.45 stable; plan the 1.0 upgrade): SQL-like, typed, light; migrations generated by drizzle-kit, committed, applied by a dedicated `migrate` entrypoint under an advisory lock, before `server` and `worker` start.
- **pg-boss 12** for jobs **and** as the transactional outbox: `boss.send(…, { db: fromDrizzle(tx, sql) })` (`sql` from `drizzle-orm`) enqueues within the business transaction, so a job or event exists if and only if the transaction commits. No Redis, no outbox table.
- Consumers are idempotent. Job progress and per-item status are stored in the owning module's tables.

### Consequences

- Good: one stateful service (PostgreSQL) besides object storage.
- Good: durable jobs survive restarts; stop/retry are explicit.
- Bad: pg-boss throughput is lower than Redis queues — irrelevant at our scale (AI calls are the bottleneck).
