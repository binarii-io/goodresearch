# synthesis

Every prompt that writes prose (insights, recommendations, takeaways, translations) includes the shared style guide (`WRITING_STYLE` and the register of its kind of text, `@goodresearch/shared`): a human voice, not a robotic one.

The project-level synthesis (context map #7 Synthesis): **insights** (spec 013), findings across the facts of a project's studies; then **recommendations** and the **key takeaways** (spec 014); last, the **debrief deck** (spec 015). The AI proposes, a person decides.

- **Sources** (`application/ports.ts` `SynthesisSources`, wired in `compose.ts`): the project and its studies with each person's folder access (research), the guides' theme sections, the accepted facts (`reads.projectFacts` / `reads.factsByIds` of `evidence`, with their participants' codes, never the verbatims' text), the known names, the person's language. Synthesis never reads another module's tables.
- **Find insights** (`commands/insight-run-commands.ts`, queue `synthesis.insights`, one run per project): the studies chosen (only those the person can open), the scope (`all`, or `unlinked`: facts in no insight) and `withProposed` (also the facts still to decide). `domain/fact-lines.ts` writes one line per fact, `fN | polarity | tN | code | statement` (code `P01`, or `S2-P01` with several studies), in the runner's language; over 40,000 characters, lines are cut by theme (`batches`), 2 calls at once, each with the insights of its themes (`iN`) and the rejected ones' statements to avoid. `domain/insights.ts` `checkInsights` keeps known refs only, drops an insight without support, with an unknown theme, a name or a percentage in its statement, removes the sentences with a percentage from the other texts, and keeps at most 25 new insights (most supporting participants first); `mergeInsights` adds new ones as proposed, replaces the texts and AI links of an insight still proposed, adds only `suggested` links to a decided one, leaves a rejected one and a fact a person unlinked alone, and drops a reproposal (60% of the words, or the same support, of a rejected insight). Each call is saved in one transaction (`applyRun`); an insight a person changed meanwhile is skipped. A call is tried twice; a stop is checked between calls and before keeping an answer; any other failure ends the run as `INTERRUPTED`, and a run whose worker stopped beating shows as interrupted. A guide section named "Other" is the built-in Other.
- **Computed, never stored** (`domain/confidence.ts`, `domain/links.ts`): the panel (participants with accepted facts in the project), confidence (high from max(5, 30% of the panel) supporting participants, medium from 3, lowered one level by counter-evidence from half as many), polarity, and each link's fact now (`accepted`, `changed`, `not-accepted`, `deleted`, `outside`) against the snapshot the link keeps; a fact still to decide is `to-decide`: shown "to validate", decided from the insight through Evidence's own route, never counted nor "changed". Only counted links to accepted facts of the project count; "Evidence changed" until "Reviewed" takes the snapshots again.
- **Decisions** (`domain/decisions.ts`, `commands/insight-commands.ts`): validate (a counted support needed), reject, edit (texts and theme; becomes `edited`, reviews its facts), validate all shown, link a fact as support or counter (one role per fact; accepts a suggested one), unlink or dismiss (kept `unlinked`), create by hand (validated, origin `person`), each with the version seen. A text written in one language is translated by the queue `synthesis.translate` while those words are still the insight's, applied again on the insight as it is if it was decided meanwhile; a translation too long, or a statement holding a known name, is not kept (`not-translated`), and "Translate again" sends the fields still to translate from the language they were written in (`pending_translation`). A text cleared is cleared in both languages.
- **Read models** (`queries/insight-queries.ts`): the tab (cards by theme, filters, counts, the last run, the costs), an insight with its facts grouped by participant, and the paged facts panel (25 per page, search, polarity, theme, study, "not in any insight"); a study the person cannot open shows its facts as counts, without statements.
- Ledger: tasks `insights`, `insight-translation`; refs `insights:<runId>:<n>` and `insights-translation:<projectId>`; the costs are shown on the Insights tab. Consent: `synthesis_consents` (person, project), asked again when the provider changes.
- Tables (migrations `0032_project_insights.sql`, `0033_insights_with_proposed_facts.sql`, `0034_insight_pending_translation.sql`): `synthesis_runs`, `synthesis_insights`, `synthesis_insight_facts` (no foreign key to the facts, Evidence's table), `synthesis_consents`; cascade with the project.

## Recommendations and key takeaways (spec 014)

- **Insights as recommendations read them** (`application/insights-now.ts`): the project's insights with their computed confidence level, polarity and participants, from the Insights tab query (`now`).
- **Find recommendations** (`commands/recommendation-run-commands.ts`, queue `synthesis.recommendations`, one run per project): the validated insights, and those still to decide when asked, sent as `iN | theme | level | polarity | for N against M of P participants | F facts | statement`, with the existing recommendations (`rN`) and the rejected actions to avoid. No fact, name, study or owner is sent.
  - `domain/recommendations.ts` `checkRecommendations` keeps known refs, values within their lists, lengths, no name in the action, and at most 15 new ones.
  - `mergeRecommendations` is incremental as for insights: decided ones keep their texts and get `suggested` links; a reproposal is dropped.
  - A stop is checked before the call and before keeping its answer; any other failure ends the run as interrupted.
- **Computed, never stored**:
  - `priority` = impact × 2 − effort;
  - `kindShown`: a build resting only on low-confidence insights shows as a test;
  - `linkStateOf`: `validated`, `to-decide`, `rejected`, `deleted`, `changed`, against the snapshot each link keeps;
  - `insightsChanged`.
- **Decisions** (`commands/recommendation-commands.ts`): validate (a counted validated insight needed), reject, edit in place (texts, kind, impact, effort, owner), validate all shown, link, unlink, accept a suggested insight, reviewed, write one by hand. Texts are translated through `application/translation.ts` (`runTranslation`, `givenTexts`: the rules of spec 013, shared with the key takeaways); the translate queue routes by `target`.
- **Key takeaways** (`commands/takeaways-commands.ts`, `domain/takeaways.ts`):
  - one row per project, saved at the version seen;
  - a draft (queue `synthesis.takeaways`) gets the takeaways saved (to revise them rather than start again), each insight with its weight (participants for and against out of the panel, facts) and an overview of the whole as counts (panel, insights by confidence, theme and polarity, recommendations by kind), never a share;
  - a draft, from the validated insights and recommendations and, on request, those still to decide (marked for the AI, then counted as "to validate" on the saved text), keeps 2 to 4 sentences without a percentage or a known name and is never saved by itself ("Use this draft");
  - `savedOver` (the validated insights and recommendations as their meaning goes: status, who decided and when, the run, an insight's confidence; never the version, which a translation or a review raises) tells "May be out of date"; a failed draft keeps the one before.
- Ledger: tasks `recommendations` and `takeaways`; refs `recommendations:<runId>:<n>`, `takeaways:<projectId>` (drafts), `takeaways-translation:<projectId>` and `recommendations-translation:<projectId>`.
- Tables (migrations `0035_project_recommendations.sql`, `0036_takeaways_with_proposed.sql`, `0037_takeaways_draft_basis.sql`): `synthesis_recommendation_runs`, `synthesis_recommendations`, `synthesis_recommendation_insights` (no foreign key to the insight), `synthesis_takeaways`; cascade with the project.

## Debrief deck (spec 015)

- **Built on the fly, never stored** (`domain/deck.ts` `buildDeck`, typed slides), as the prototype's deck: title (interviews, period, participants, team), what to remember (key takeaways and the top three recommendations), context, method (a card per study: retained interviews, guide themes and question count), numbers (with the panel; no separate panel slide), insights at a glance (what works, what holds back, the other findings; 6 rows a slide), one slide per insight, nuances (not "None"; 4 a slide), recommendations (6 rows, by priority then support; evidence = the lowest confidence of their counted insights), the impact × effort matrix, who does what, thanks (no limits slide for now: product decision). A section without content is left out, except the title and the thanks. Only what is validated (or edited); with `withProposed`, also what is still to decide, marked "to validate"; every figure then counts their facts too (`insightsNow` with `withToDecide`: participants for and against, panel, confidence, polarity, supporting facts, a recommendation's evidence), and the numbers slide says how many participants are known only from such facts. With `withProposed`, the AI draft of the key takeaways not used yet stands in for the saved text, flagged as a draft to validate. Insights are numbered most solid first (confidence, supporting participants, facts).
- **Verbatim**: the emblematic one per insight, from its supporting facts that count as the figures do (accepted, and still to decide when included; never rejected, deleted or from a closed study) (`reads.verbatimsOf` of `evidence`): 40 to 320 characters, the closest to 140; the names the app knows replaced (`[…]`), cut at a word. Studies the person cannot open give neither facts, verbatims nor counts: the insights' figures are computed over the open studies only (`application/debrief-deck.ts`). The guide's own theme numbering ("Theme 2: …") is dropped, for the app and Slides alike.
- **Next steps from the data**: the validated recommendations (or those shown) with owner or "to assign" and success measure. Nothing is typed in, no AI call.
- **Words**: the app words its slides through Lingui (`web/features/synthesis/deck-slide.tsx`); Google Slides gets the same slides worded by `domain/deck-pages.ts` `presentationOf` in the publication's language (deck content, not interface strings, as publishing's labels). The fingerprint (cyrb53 of the slides, without the day) tells "out of date".
- **Google Slides** (`commands/debrief-commands.ts`, `publish`, `update`): written through the Drive documents port of ingestion (`createPresentation`, `rewritePresentation`: Slides API `batchUpdate`, new slides first then the old ones deleted, so the same file, link and sharing; the cover slides on the brand's ink), with the person's own Drive write access, in the folder of a study of the project. The record keeps the file, folder, study, language, option, the studies it was built from, the fingerprint and the presentation's content revision after the app wrote it. An update writes only at that revision, checked in the write itself (`writeControl.requiredRevisionId`): a change made in Google Slides, even meanwhile, is replaced only with `replace` (`DECK_CHANGED_IN_SLIDES` otherwise); sharing or renaming the file does not count. A file trashed or gone gives `DECK_FILE_GONE`; a new publication creates a new file and the old one stays in Drive (nothing is ever deleted there). Review of PR #15:
  - an update claims the record (version) before writing, so of two at once the second writes nothing (`VERSION_CONFLICT`);
  - a revision not read after a write counts as a change (asks before replacing); who published and when change only once the file is written;
  - a file created but left empty (Slides failure) is kept, shown out of date, and `publish` says `DECK_NOT_WRITTEN`;
  - the record keeps the studies it was built from: someone who cannot open all of them sees neither "out of date" nor "in sync", and cannot update it (`DECK_ACCESS_DIFFERS`); a study added since, open to the person, is taken in;
  - one read of the project builds the deck shown and the deck as published;
  - French Slides words use the glossary and a non-breaking space before colons.
- Table (migration `0038_debrief_deck.sql`): `synthesis_published_decks`; cascade with the project.

## Project overview (spec 017)

The Overview tab is read by the `reporting` module. Synthesis gives it `overviewReads` (`queries/overview-reads.ts`: SQL counts, the takeaways' text, ledger refs) and serves `GET .../takeaways/freshness` itself (`queries/takeaways-queries.ts`).
