# usability

The analysis of usability test sessions (spec 038, ADR-0013), context map: Usability analysis.

- **Run** (`commands/analysis-run.ts`): the ready sessions of a study (spec 037 readiness) analysed in the worker, one run per study (queue `usability.analysis`, table `usability_analysis_runs`), sessions one after another, stop checked between stages, heartbeat at each stage. The estimate before a run is the video minutes times the trial's tokens per minute and tier (`domain/estimate.ts`), priced by the gateway; each session also carries its own estimate (minutes times the price of a minute) for its own "Analyse" button, which starts a run of that session alone. Starting needs the folder consent for the provider (spec 022) and a provider that reads video (Vertex AI, or the dev fake). The protocol version is frozen on the analysis when it starts; a changed version or video makes it out of date.
- **Pipeline** (`pipeline/run-session.ts`): the video streamed from Drive to the staging bucket by parts of a resumable upload (never whole in the worker), ffmpeg reading the copy over https by ranges with a short-lived access (ADR-0013 update), layout (crop of the shared screen, read on 960-wide frames and scaled by ffmpeg to the video's own size, kept inside the picture), transcript by 18-minute chunks overlapping by one minute (a moment belongs to one chunk), screen log from keyframes every 3 s (small JPEG files read by batches, each removed once read), task map, one reading per task on its part of the video (3 at a time), observations kept only with a quote found in the transcript and a moment within the task, judge on frames ±6 s (every second) and ±20 s (every 4 s) that never rejects without contrary evidence, arbiter (strong tier) on every doubt, screenshot at each moment. Copies and work files are removed in a `finally`. People are proposed from the transcript when the session has none (Ingestion's spec 009 rules). Prompts: `infrastructure/prompts/analysis-ai.ts`; the dev provider answers them in `ai-gateway/infrastructure/fake-usability.ts`.
- **Review** (`commands/observation-commands.ts`): accept, edit, reject, reopen an observation at the version seen; add one by hand; correct a task's outcome. Since spec 039 every observation (not a SUS answer, not rejected by the checks unless a person decided it) has a Fact of source `usability` with its status, through Evidence's `observationFacts`: to decide after the analysis (`syncSession`), then decided with the observation; a rejected observation keeps its fact, rejected. Each task's decided outcomes give a task fact (`syncTasks`, after an analysis and after each outcome decided). Evidence decides an observation's fact through the `UsabilityDecisions` port wired in `compose.ts`, so the two never disagree. When the worker starts, `backfillFacts` gives their facts to sessions analysed before (a fact already up to date is not written again). A new analysis keeps decided items and never proposes again a rejected one.
- **Reads** (`queries/analysis-queries.ts`): the study's sessions with their analysis state and cost; one session with its tasks, observations, rejected ones and transcript; the study results (outcome counts, median time, difficulties by session, ease, SUS by the standard scoring) from decided items only, tasks matched by id across protocol versions.
- Ledger: tasks `usability-layout`, `usability-transcript`, `usability-screen-log`, `usability-task-map`, `usability-task`, `usability-judge`, `usability-arbiter`; ref `usability-analysis:<sessionId>` (also the facts' translations), shown per session and per study.
- Tables: `usability_analyses` (one per session, its id kept by a new analysis), `usability_transcripts`, `usability_task_results`, `usability_observations`, `usability_screenshots` (no foreign key: the sweep deletes images nothing refers to), `usability_analysis_runs` (`0062`); cascade with the session and the study.
- Routes: `/api/studies/:studyId/usability/{analysis,analysis/runs,results}`, `/api/usability/sessions/:id` (and `/video`, a Range proxy to Drive), `/api/usability/observations/:id/{decision,screenshot}`, `/api/usability/task-results/:id`; reserved to the team with the folder open.

## Robustness

- A running job beats every minute, so a long stage never looks stale; a job whose run was stopped or replaced stops at its next checkpoint and never saves over the new run's analysis. The run is finished last, in a `finally`.
- A failure reading one session or its protocol fails that session only. When the queue refuses a new job (the previous one still ending), each session's analysis is put back as it was.
- What the model returns is kept within what the tables hold (a moment never before 0, SUS values only on SUS answers).
- A decision writes the fact first: a statement naming a person is refused (`NAME_IN_STATEMENT`) and the observation stays as it was. An observation always belongs to a task.
- Results read every analysis whatever its state: decided items stay while a session is analysed again.
- The player's range requests read the session's row only; items to review are counted in SQL.
- When the AI provider refuses the person's access (a Google grant to renew), the analysis fails with `AI_RECONNECT_REQUIRED`, not as a copy failure, and the person's connection turns "needs attention" as after any refused call; they reconnect it (or remove it, the shared provider then serves them) before analysing again.
- A run left by a worker that stopped (a restart, a redeployment) has no heartbeat: `recoverStaleRuns`, when the worker starts, once more 11 minutes later, then with the hourly sweep, closes it after 10 minutes (`RUN_STALE_MS`) without one and marks its sessions still waiting or being analysed "stopped" (`stopRunAnalyses`, one conditional update), so they can be analysed again instead of showing a step forever. The job beats once when it starts, so a run still queued behind another study's job (no heartbeat since its start) is never taken for a dead one. A run replaced at start because it looked stale has its sessions stopped the same way.
